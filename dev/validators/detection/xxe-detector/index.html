    XxeDetector¶

    Flag text carrying an XML External Entity (XXE) construct.

    Description¶

    XxeDetector is a deterministic, text-only, detect-only validator. It runs under Guard and reports a failure when the content carries an XXE-capable XML construct — an external entity, an external or inline DTD, an entity declaration, or XInclude; it never changes the content. Use it as a cheap, non-LLM check at a trust boundary on input (or model output) that could, now or downstream, reach an XML processor.

    Guard runs its registered validators concurrently, so a failure here does not short-circuit or skip other validators — "cheap" refers to this validator's own cost.

    Obfuscation is decoded before detection¶

    Real payloads hide behind encoding layers, so the content is preprocessed before any pattern runs: invisible/zero-width control characters are stripped, then URL-percent, HTML-entity, JavaScript \uXXXX/\xXX, and CSS \3C escapes are decoded repeatedly until the text stops changing (bounded). Without this, %3C!DOCTYPE or &#x3C;!ENTITY would sail past a raw-text matcher. Each pass can be disabled via the constructor when the input's encoding is fully trusted.

    Declarations inside inert regions are not flagged¶

    A declaration written inside a complete comment (<!-- -->), CDATA section (<![CDATA[ ]]>), or processing instruction (<? ?>) is data, not markup — an XML processor never acts on it — so those complete regions are blanked out before the patterns run. This removes the classic "matcher fires on <!DOCTYPE inside a comment" false positive without parsing hostile XML. An unterminated region is treated the opposite way: it cannot make what follows inert, so a construct after an unclosed comment or CDATA is still flagged (fail toward detection).

    What it flags¶

    Capability-bearing DTD/entity machinery and XInclude — not every < or &:

    • external_entity — an entity declaration (general or % parameter) carrying an external ID: <!ENTITY xxe SYSTEM "file:///etc/passwd">, <!ENTITY p PUBLIC "id" "http://host/">. The file-read / SSRF vector.
    • external_dtd — a DOCTYPE pointing at an external subset: <!DOCTYPE foo SYSTEM "foo.dtd">.
    • dtd_internal_subset — a DOCTYPE opening an inline [ ... ] subset, where entity bombs (billion laughs) and internal entities live: <!DOCTYPE foo [ <!ENTITY x "..."> ]>.
    • parameter_entity — a parameter-entity declaration <!ENTITY % ...>, the blind/out-of-band building block.
    • entity_declaration — any other entity declaration, the billion-laughs building block. Presence is the signal; the validator never expands it to classify (CWE-776).
    • xinclude — the XInclude namespace http://www.w3.org/2001/XInclude or an <xi:include> element, which pulls in an external file/URL without a DTD. Matching the namespace URI itself (not just an <xi:include> element) catches a renamed prefix, at the cost of flagging input that merely names the URI — a bare xmlns:xi="…/XInclude" declaration, or prose quoting the spec URL, will trip this. That false positive is intentional (bias to recall). A non-xi prefix bound to the XInclude namespace out of view (an <p:include> element whose xmlns binding sits on an ancestor that is not in the rendered text) is not caught — a limitation of a text scanner that does not resolve namespace scope across a document it may see only in part.
    • bare_doctype — a capability-free bare <!DOCTYPE name>. Only flagged when flag_bare_doctype=True (see below); off by default so a bare HTML5 doctype passes.

    Matching is case-insensitive and every pattern is linear (no nested quantifier that can backtrack), so the validator adds no ReDoS surface of its own.

    The safety ceiling — read before you rely on this¶

    This validator is defense-in-depth, not a primary control. The authoritative XXE defense is a hardened XML parser at the processing site — DTDs disabled, external entities disabled, no external resolution. A passed result means "no known XXE construct found", never "provably safe". Byte-level transport tricks (UTF-16/UTF-32 BOM, base64- or archive-wrapped XML) are out of scope by design: they belong to an upstream decode/extraction stage that hands this validator a decoded string.

    Constructor Parameters¶

    Parameter Type Default Description
    strip_invisible_chars bool True Strip zero-width/control characters before matching.
    decode_obfuscation bool True Decode URL/HTML/JS/CSS encoding layers before matching.
    max_input_chars int \| None 1048576 (1 MiB) Resource valve. When the view's items exceed it in combined character length, the input is rejected with XXE_INPUT_TOO_LARGE rather than preprocessed and scanned. Pass None to lift the cap when the input size is already trusted. Negative values raise ValueError.
    flag_bare_doctype bool False Also flag a capability-free bare <!DOCTYPE name> (reject-all-DOCTYPE policy). Off by default so a bare HTML5 doctype passes.

    Each item is decoded and inert-masked on its own, then the items are flattened (via ContentView.render()) for matching. A construct split across an item boundary (<!DOCTYPE foo + SYSTEM "...">) is still caught — render() joins items with a newline, matched by \s — while an inert region (comment/CDATA/PI) in one item cannot mask a construct in another, since the parts may be processed separately downstream.

    Usage¶

    from aegis import Guard
from aegis.validators.detection import XxeDetector

guard = Guard("input").use(XxeDetector())

result = await guard.validate('<!DOCTYPE foo SYSTEM "file:///etc/passwd">')
if result.has_failures:
    print(result.failures[0].error_code)  # XXE_DETECTED

    Error Codes¶

    Error Code Condition
    XXE_DETECTED The rendered content carries an XXE-capable construct (after decoding and inert-region masking).
    XXE_INPUT_TOO_LARGE max_input_chars is set and the combined length of the view's items exceeds it.

    Failure Details¶

    XXE_DETECTED locates the first construct (the raw matched text is never echoed):

    Field Type Description
    match_offset int Start position of the earliest construct, into the decoded/stripped/masked text that was scanned — not the raw input, since decoding shifts offsets.
    match_length int Length of the matched construct.
    construct str The construct class: external_entity, external_dtd, dtd_internal_subset, parameter_entity, entity_declaration, xinclude, or bare_doctype.

    XXE_INPUT_TOO_LARGE carries:

    Field Type Description
    length int The combined character length of the view's items that exceeded the limit.
    limit int The configured max_input_chars.

    Flags text carrying an XXE-capable XML construct, after decoding obfuscation.

    A detect-only validator for the Guard path. Each item is first decoded (see the module docstring) and its complete comment/CDATA/PI regions blanked out, then the items are flattened for matching; validate reports a failure if the content carries an external entity, an external or inline DTD, an entity or parameter-entity declaration, or XInclude. It never rewrites the content — an XXE payload is refused, not laundered, since stripping a DTD can silently change the document's meaning.

    DTD handling is capability-based: a bare <!DOCTYPE html> (no external ID, no internal subset) carries no XXE capability and passes by default. Set flag_bare_doctype=True to reject every DOCTYPE for a strict deployment.

    This is defense-in-depth, not a primary control — the authoritative XXE defense is a hardened XML parser at the processing site. A passed result means "no known XXE construct found", not "provably safe".

    The decode/strip passes defeat encoded payloads; a caller who fully trusts the encoding of

    Args:
        strip_invisible_chars: Strip zero-width/control characters wedged into a keyword to dodge
            a match — deobfuscation, not Unicode normalization.

            and scanned, bounding the per-request work (several decode passes plus a per-character

            cap abuse; pass ``None`` to lift the cap when the input size is already trusted.

            flagged (as ``bare_doctype``). Off by default, so a bare HTML5 doctype passes.

    Raises:
        ValueError: If ``max_input_chars`` is negative.

    if max_input_chars is not None and max_input_chars < 0:
        raise ValueError(f"max_input_chars must be non-negative, got {max_input_chars}.")
    self.strip_invisible_chars = strip_invisible_chars
    self.decode_obfuscation = decode_obfuscation
    self.flag_bare_doctype = flag_bare_doctype
    self._max_input_chars = max_input_chars

    async def validate(
    self,
    view: ContentView,
    metadata: GuardMetadata | None = None,
) -> ValidationResult:
    """Report whether the rendered content carries an XXE-capable construct (after decoding).

    Each item is decoded and inert-masked on its own, then the masked items are flattened through
    ``ContentView.render()`` for matching — so a construct split across an item boundary is still
    caught (``render()`` joins with whitespace, matched by ``\\s``), while an inert region in one
    item cannot mask a construct in another.

    Args:
        view: The content under inspection. Never ``None``, but may be empty.
        metadata: Surrounding agent context. Optional and unused here.

    Returns:
        ``PassedResult`` when no XXE construct is found. Otherwise a ``FailedResult`` carrying
        ``XXE_DETECTED`` with ``details`` locating the first construct — ``match_offset`` and
        ``match_length`` (into the decoded/stripped/masked text that was scanned, **not** the raw
        input, since decoding shifts offsets) and ``construct`` (the construct class, e.g.
        ``"external_entity"``, ``"dtd_internal_subset"``). Or ``XXE_INPUT_TOO_LARGE`` when
        ``max_input_chars`` is set and exceeded. The raw input — and any path, URL, or name
        inside it — is never echoed; only safe summaries are reported.
    """
    # Resource valve first: reject oversized input before any decode/scan. The cap bounds the
    # total text the scan will process — the sum of the item values — so many just-under-limit
    # items cannot blow up the aggregate work. Summing item lengths (rather than measuring
    # ``view.render()``) keeps the valve off render()'s internal format: the separators it places
    # between items are its concern, not work this validator does.
    total_length = sum(len(item.value) for item in view.items)
    if self._max_input_chars is not None and total_length > self._max_input_chars:
        return FailedResult(
            error_message=f"Text exceeds the {self._max_input_chars}-character inspection limit.",
            error_code=self.XXE_INPUT_TOO_LARGE,
            details={"length": total_length, "limit": self._max_input_chars},
        )

    # Decode and inert-mask each item on its own (see _decode_and_mask: one item's inert region
    # must never make another item's construct inert), then let render() flatten the masked
    # items. Delegating the join to the view keeps the scan aligned with however render()
    # flattens it, rather than hardcoding a separator here.
    masked_view = ContentView(items=tuple(self._decode_and_mask(item) for item in view.items))
    scanned = masked_view.render()
    match = _find_xxe(scanned, flag_bare_doctype=self.flag_bare_doctype)
    if match is not None:
        start, end, construct = match
        return FailedResult(
            error_message=f"Input contains an XXE construct ({construct}) at offset {start}.",
            error_code=self.XXE_DETECTED,
            details={"match_offset": start, "match_length": end - start, "construct": construct},
        )
    return PassedResult()
